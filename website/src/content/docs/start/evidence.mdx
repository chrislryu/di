## How to interpret this evidence

The map shows selected, inspected relationships rather than a complete support matrix. A dependency is required only for the specified implementation or path. An optional integration must be selected and configured. Alternatives can solve related problems while exposing different APIs and deployment scopes.

Each linked revision is independently pinned. Source inspection establishes responsibilities and handoffs; a runtime experiment must also record compatible package versions, build features, drivers, hardware, model artifacts, and configuration. None of these traces is a measured performance comparison.

<h2 id="vllm-nccl">vLLM → NCCL during model execution</h2>

A distributed model layer can produce partial outputs that need a collective.
vLLM routes that operation through its group/device communicator. The NCCL
implementation calls `ncclAllReduce` on the execution stream. GPU communication
is part of the model's execution path; the selected communicator determines its
implementation.

- [vLLM: parallel model layers](https://github.com/vllm-project/vllm/blob/9a56d4fec6b0a30a0a989f1cd06cd3c2f7325619/vllm/model_executor/layers/linear.py)

## Known limits of the review

- The public DeepInfer release omits parts of a full hosted service, including the external KV system and service-level disaggregation/load balancing. Its internal attention cache is still necessary for model execution.
- The DeepEP MoE trace isolates communication with synthetic tensors; it does not claim a complete serving-engine integration.
- The AWS path is selected explicitly. Merely using an AWS instance, an EFA-capable device, or NCCL does not prove the plugin/provider was selected.
- NIXL backend selection and available integrations depend on the build and configuration. A plugin source directory does not establish that every distribution includes it.
- GPU execution, multi-node behavior, and performance were not tested while writing the website. The exercises remain usable through source inspection.
